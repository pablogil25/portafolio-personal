# Content Strategy

Este documento define la arquitectura de contenido del portafolio de Pablo Rodriguez Gil. Su funcion es decidir que decir, en que orden decirlo y por que cada pieza de informacion ayuda a conseguir entrevistas.

## Objetivo Del Contenido

El contenido debe posicionar a Pablo como un Software Developer practico, tecnico y confiable, con experiencia en proyectos reales, automatizacion, backend, APIs y desarrollo web.

El visitante debe entender rapidamente:

- Que hace.
- Que tecnologias domina.
- Que problemas puede resolver.
- Que proyectos respaldan su perfil.
- Como contactarlo.

## Tono De Voz

El tono debe ser:

- Directo.
- Profesional.
- Preciso.
- Seguro sin exagerar.
- Tecnico pero entendible para reclutadores.

Evitar:

- "Soy apasionado por la tecnologia" como idea principal.
- Frases infladas sin evidencia.
- Listas largas sin contexto.
- Promesas que no puedan demostrarse con proyectos.

Decision:
La confianza nace de la claridad. El tono debe parecerse mas a un producto bien presentado que a una biografia informal.

## Mensaje Central

Pablo Rodriguez Gil es un Software Developer que construye soluciones web, backend, APIs y automatizaciones con Python, JavaScript, Node.js, React, Laravel, PHP, MySQL y Git.

Ese mensaje debe repetirse con variaciones a lo largo del sitio:

- En el inicio como posicionamiento.
- En capacidades como problemas que resuelve.
- En proyectos como evidencia.
- En contacto como razon para conversar.

## Jerarquia De Contenido

### Nivel 1: Identidad Profesional

Contenido:

- Pablo Rodriguez Gil.
- Software Developer.
- Backend, automatizacion, APIs y desarrollo web.

Funcion:
Orientar al visitante de inmediato.

Justificacion:
Si el usuario no entiende quien es Pablo en los primeros segundos, los proyectos pierden contexto.

### Nivel 2: Valor Profesional

Contenido:

- Desarrollo de software.
- Automatizaciones con Python.
- REST APIs.
- Backend Development.
- Aplicaciones con React.
- Sistemas con Laravel, PHP y MySQL.

Funcion:
Explicar que puede resolver.

Justificacion:
Los reclutadores y lideres tecnicos buscan encaje con problemas, no solo herramientas.

### Nivel 3: Evidencia

Contenido:

- RapiMecanica.
- GoClean.
- Automatizaciones.
- Repositorios de GitHub.
- Certificados seleccionados.

Funcion:
Demostrar que el perfil no es solamente declarativo.

Justificacion:
La evidencia debe llegar rapido, pero despues de explicar el valor para que tenga significado.

### Nivel 4: Validacion Externa

Contenido:

- GitHub.
- LinkedIn.
- CV descargable.
- Certificados.

Funcion:
Dar caminos de verificacion y contacto.

Justificacion:
Un portafolio efectivo no intenta contenerlo todo. Debe abrir puertas hacia pruebas externas.

## Informacion Antes De Mostrar Proyectos

Antes de mostrar proyectos, el sitio debe explicar:

- Rol profesional.
- Especialidades principales.
- Tipos de problemas que Pablo resuelve.
- Tecnologias principales.
- Participacion en proyectos reales.

Decision:
Mostrar proyectos demasiado pronto puede hacer que el visitante los evalua como piezas aisladas. Presentar primero el marco profesional hace que cada proyecto se lea como prueba de una capacidad concreta.

## Proyecto Principal

El Featured Project debe ser RapiMecanica.

Motivos:

- Tiene nombre de producto real.
- Sugiere un problema concreto y entendible.
- Permite explicar flujos, usuarios, datos y logica de negocio.
- Puede mostrar backend, APIs, base de datos y experiencia de producto.
- Ayuda a diferenciar a Pablo de perfiles con proyectos academicos genericos.

Contenido recomendado:

- Contexto del problema.
- Objetivo del proyecto.
- Rol de Pablo.
- Funcionalidades principales.
- Stack usado.
- Decisiones tecnicas.
- Retos encontrados.
- Resultado o aprendizaje.
- Enlaces disponibles.

## Orden De Proyectos

### 1. RapiMecanica

Debe aparecer primero como proyecto destacado.

Por que:
Es el mejor candidato para contar una historia completa de producto y capacidad tecnica.

### 2. GoClean

Debe aparecer despues como segundo proyecto real.

Por que:
Refuerza que Pablo no tiene una sola experiencia aislada. Muestra continuidad y participacion en mas de un producto.

### 3. Automatizaciones Con Python

Debe aparecer como categoria o caso tecnico.

Por que:
La automatizacion es una ventaja diferencial frente a muchos desarrolladores junior. Comunica eficiencia, pensamiento sistemico y capacidad para ahorrar tiempo.

### 4. Proyectos De Soporte

Deben aparecer solo si refuerzan una habilidad importante.

Por que:
No todos los proyectos merecen el mismo peso. Es mejor mostrar menos proyectos con mejor narrativa que muchos sin impacto.

## Presentacion Del Stack Tecnologico

El stack no debe mostrarse como una nube de logos. Debe organizarse por uso:

- Lenguajes: Python, JavaScript, PHP.
- Backend: Node.js, Laravel, REST APIs.
- Frontend: React.
- Datos: MySQL.
- Herramientas: Git.
- Diferencial: automatizacion con Python.

Cada grupo debe responder:

- Para que lo usa Pablo.
- En que proyectos aparece.
- Que problema ayuda a resolver.

Decision:
Una persona tecnica puede escanear tecnologias. Una persona de reclutamiento necesita entender aplicacion y contexto.

## Presentacion De Experiencia Profesional

La experiencia debe presentarse como "experiencia aplicada", no solo como historia laboral.

Formato conceptual recomendado:

- Proyecto o contexto.
- Responsabilidad.
- Tecnologia usada.
- Resultado o aprendizaje.

Contenido:

- Participacion en RapiMecanica.
- Participacion en GoClean.
- Automatizaciones con Python.
- Desarrollo de software.
- Backend y APIs.

Decision:
Para un perfil junior, la experiencia gana fuerza cuando se conecta con responsabilidades concretas y no con cargos inflados.

## Presentacion De Certificados

Los certificados deben aparecer despues de proyectos, experiencia y stack.

Reglas:

- Mostrar solo los mas relevantes.
- Agrupar por area.
- Evitar una galeria extensa en la pagina principal.
- Ofrecer una opcion para ver mas si hay muchos.
- Priorizar certificados relacionados con Python, backend, JavaScript, React, Laravel, bases de datos y Git.

Decision:
Los certificados validan aprendizaje, pero los proyectos validan capacidad. Por eso los certificados deben respaldar, no liderar.

## Presentacion De GitHub

GitHub debe mostrarse como evidencia tecnica verificable.

Contenido recomendado:

- Enlace al perfil.
- Repositorios destacados.
- Repositorios conectados a proyectos del portafolio.
- Mencion de buenas practicas visibles: README, estructura, commits, uso de Git.

Ubicacion:

- Enlaces puntuales dentro de proyectos.
- Seccion propia despues del stack o despues de proyectos.
- Contacto final como enlace secundario.

Decision:
GitHub debe aparecer cuando el visitante ya tiene contexto para interpretar el codigo.

## Presentacion De LinkedIn

LinkedIn debe funcionar como canal de confianza y contacto.

Contenido recomendado:

- Enlace visible.
- CTA claro: "Conectar en LinkedIn".
- Mensaje de disponibilidad profesional.

Ubicacion:

- En hero como enlace secundario.
- En contacto final como accion destacada.
- Opcionalmente en una franja de validacion profesional.

Decision:
LinkedIn es especialmente importante para entrevistas porque permite verificar identidad, trayectoria y contacto rapido.

## Descarga Del CV

El boton para descargar el CV debe aparecer:

- Como accion secundaria discreta en el inicio.
- Despues de los proyectos si el visitante ya vio evidencia.
- En el cierre final como accion clara.

No debe reemplazar el CTA principal de contacto.

Textos recomendados:

- "Descargar CV".
- "Descargar CV completo".
- "Ver CV y contacto".

Decision:
El CV es una herramienta de seleccion, pero el portafolio debe crear interes antes de enviar al visitante a un PDF.

## Contacto Final

La pagina debe terminar con una invitacion directa:

"Si buscas un desarrollador que pueda construir backend, APIs, automatizaciones y aplicaciones web con criterio tecnico, conversemos."

Acciones finales:

- Enviar mensaje.
- Conectar en LinkedIn.
- Ver GitHub.
- Descargar CV.

Decision:
El cierre debe reducir friccion y recordar el valor principal. El visitante no debe llegar al final y preguntarse cual es el siguiente paso.

## CTAs Por Momento

### Inicio

- Principal: "Contactarme".
- Secundario: "Ver proyectos".
- Terciario discreto: "Descargar CV".

### Antes De Proyectos

- Principal: "Ver trabajo aplicado".

### Proyecto Principal

- Principal: "Ver caso de estudio".
- Secundario: "Ver codigo en GitHub".

### Despues De Proyectos

- Principal: "Hablemos sobre una oportunidad".
- Secundario: "Descargar CV completo".

### Contacto Final

- Principal: "Enviar mensaje".
- Secundario: "Conectar en LinkedIn".
- Terciario: "Ver GitHub".

## Reglas Editoriales

- Cada seccion debe tener una sola idea dominante.
- Cada proyecto debe explicar problema, solucion y rol.
- Cada tecnologia debe aparecer con contexto.
- Cada CTA debe estar justificado por el momento del recorrido.
- El contenido debe poder escanearse en menos de un minuto.
- La pagina debe evitar textos largos si no aportan evidencia.

## Medicion De Calidad Del Contenido

El contenido sera fuerte si cumple estas condiciones:

- El hero puede entenderse sin hacer scroll.
- Los proyectos explican problemas reales.
- El stack se entiende por contexto.
- Los certificados no saturan.
- GitHub y LinkedIn aparecen como validacion.
- El CV aparece sin robar protagonismo.
- El cierre invita a contactar de forma natural.
