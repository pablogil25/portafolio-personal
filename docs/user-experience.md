# User Experience

Este documento define el recorrido ideal del portafolio de Pablo Rodriguez Gil antes de disenar componentes visuales o escribir codigo. El objetivo no es crear una pagina bonita, sino una experiencia que ayude a conseguir entrevistas, genere confianza y comunique capacidad tecnica en pocos segundos.

## Principio UX Principal

El sitio debe funcionar como una conversacion profesional muy bien ordenada:

1. Quien soy.
2. Que problemas puedo resolver.
3. Que evidencia real tengo.
4. Como trabajo.
5. Como contactarme.

La inspiracion viene de Apple, Stripe, Linear, Vercel, GitHub, Framer y Notion: claridad antes que decoracion, jerarquia fuerte, copy directo, evidencia visible y progresion natural hacia la accion.

## Recorrido Ideal Del Usuario

### 0 a 5 segundos

El visitante debe sentir claridad inmediata.

Debe entender:

- Pablo Rodriguez Gil es Software Developer.
- Trabaja con Python, JavaScript, Node.js, React, Laravel, PHP y MySQL.
- Puede construir backend, APIs, automatizaciones y software real.
- Hay proyectos concretos detras del perfil.

Decision: los primeros segundos no deben gastarse en frases genericas como "bienvenido a mi portafolio". La pantalla inicial debe responder rapidamente "quien es", "que hace" y "por que deberia seguir leyendo".

### 5 a 30 segundos

El visitante debe sentir interes y confianza inicial.

Debe ver senales de:

- Experiencia practica en proyectos reales.
- Capacidad para resolver problemas operativos.
- Stack tecnico coherente.
- GitHub y LinkedIn disponibles como prueba externa.

Decision: antes de mostrar muchos proyectos, el sitio debe explicar el tipo de valor que Pablo aporta. Esto aumenta la probabilidad de que los proyectos se lean como evidencia, no como una galeria sin contexto.

### 30 a 90 segundos

El visitante debe sentir que vale la pena revisar el trabajo.

Debe encontrar:

- Un proyecto principal con contexto, problema, rol, tecnologia y resultado.
- Proyectos secundarios ordenados por impacto.
- Experiencia presentada como capacidades aplicadas.
- Certificados como soporte, no como protagonista.

Decision: un reclutador no necesita ver todo de inmediato. Necesita encontrar senales confiables en el menor tiempo posible y profundizar solo si algo le interesa.

### Final Del Recorrido

El visitante debe sentir seguridad para contactar.

Debe terminar con:

- Una invitacion concreta a conversar.
- Opciones claras: LinkedIn, email, GitHub y descarga de CV.
- Refuerzo de disponibilidad profesional.

Decision: la pagina debe cerrar como una propuesta profesional, no como una despedida pasiva.

## Orden De Secciones Recomendado

Este orden evita el patron tradicional de "hero, sobre mi, skills, proyectos, contacto" y prioriza impacto, evidencia y conversion.

1. Posicionamiento profesional.
2. Prueba rapida de valor.
3. Capacidades tecnicas aplicadas.
4. Proyecto principal destacado.
5. Proyectos reales complementarios.
6. Forma de trabajo y criterio tecnico.
7. Experiencia profesional resumida.
8. Stack tecnologico por contexto.
9. GitHub como evidencia tecnica.
10. LinkedIn y confianza profesional.
11. Certificados curados.
12. CV y contacto final.

## Secciones

### 1. Posicionamiento Profesional

Objetivo:
Comunicar en menos de 10 segundos quien es Pablo, que hace y por que importa.

Informacion que debe contener:

- Nombre: Pablo Rodriguez Gil.
- Rol: Software Developer.
- Propuesta breve: desarrollo backend, APIs, automatizacion con Python y aplicaciones web.
- Tecnologias principales en una linea escaneable.
- CTA principal hacia contacto.
- CTA secundario hacia proyectos.

Tiempo aproximado:
5 a 8 segundos.

Emocion:
Claridad, seguridad y curiosidad.

Accion que debe provocar:
Continuar hacia la evidencia del trabajo o contactar si el visitante ya tiene una oportunidad concreta.

Justificacion:
Apple y Vercel presentan valor de forma directa. El portafolio debe hacer lo mismo: una promesa clara antes de cualquier detalle.

### 2. Prueba Rapida De Valor

Objetivo:
Convertir el posicionamiento en confianza inicial.

Informacion que debe contener:

- Participacion en proyectos reales: RapiMecanica y GoClean.
- Areas de impacto: automatizacion, backend, REST APIs, integracion de datos y desarrollo web.
- Tres o cuatro indicadores cualitativos, no inflados: "proyectos reales", "automatizaciones", "backend", "bases de datos".

Tiempo aproximado:
8 a 12 segundos.

Emocion:
"Esta persona ya ha trabajado en cosas concretas".

Accion que debe provocar:
Preparar al visitante para revisar el proyecto principal.

Justificacion:
Stripe y Linear crean confianza mostrando rapidamente el valor antes de profundizar. Esta seccion evita que el usuario llegue frio a los proyectos.

### 3. Capacidades Tecnicas Aplicadas

Objetivo:
Explicar que problemas puede resolver Pablo antes de listar herramientas.

Informacion que debe contener:

- Backend Development.
- REST APIs.
- Automatizacion con Python.
- Aplicaciones web con React.
- Desarrollo con Laravel y PHP.
- Manejo de MySQL.
- Versionado con Git.

Tiempo aproximado:
12 a 18 segundos.

Emocion:
Competencia practica.

Accion que debe provocar:
Hacer que el visitante quiera ver pruebas de esas capacidades.

Justificacion:
GitHub y Notion comunican utilidad agrupando conceptos. El stack no debe presentarse como una lista decorativa, sino como capacidades conectadas con problemas reales.

### 4. Proyecto Principal Destacado

Objetivo:
Mostrar la evidencia mas fuerte del perfil.

Proyecto recomendado:
RapiMecanica.

Por que debe ir primero:

- Suena como un producto con problema operativo claro.
- Permite demostrar logica de negocio, flujo de usuarios, backend, datos y posible integracion con servicios.
- Tiene mayor potencial narrativo que una lista tecnica aislada.

Informacion que debe contener:

- Problema que resuelve.
- Rol de Pablo dentro del proyecto.
- Funcionalidades principales.
- Tecnologias usadas.
- Decisiones tecnicas relevantes.
- Resultado o aprendizaje concreto.
- Enlaces disponibles: demo, repositorio o caso de estudio si existen.

Tiempo aproximado:
25 a 45 segundos.

Emocion:
Credibilidad.

Accion que debe provocar:
Abrir el caso de estudio, revisar codigo o continuar hacia mas proyectos.

Justificacion:
Vercel y Framer destacan productos o casos fuertes antes de listar todo el catalogo. Un proyecto principal da foco y evita que todos los proyectos compitan al mismo nivel.

### 5. Proyectos Reales Complementarios

Objetivo:
Demostrar amplitud sin saturar.

Orden recomendado:

1. RapiMecanica como Featured Project.
2. GoClean como segundo proyecto real.
3. Automatizaciones con Python como grupo de proyectos o caso tecnico.
4. Otros proyectos web o backend que refuercen el stack.

Por que este orden:

- Primero va el proyecto con mayor historia de producto.
- Segundo va otro proyecto real para probar continuidad.
- Despues van automatizaciones para diferenciar a Pablo de otros juniors.
- Al final van proyectos de soporte, utiles para ampliar pero no para abrir la narrativa.

Informacion que debe contener por proyecto:

- Nombre.
- Problema.
- Solucion.
- Rol.
- Stack.
- Lo mas dificil o interesante.
- Enlace a GitHub, demo o detalle.

Tiempo aproximado:
30 a 60 segundos.

Emocion:
Confianza acumulada.

Accion que debe provocar:
Elegir un proyecto para profundizar o saltar a GitHub.

Justificacion:
Los proyectos deben sentirse como evidencia profesional, no como tarjetas decorativas.

### 6. Forma De Trabajo Y Criterio Tecnico

Objetivo:
Mostrar madurez profesional mas alla del stack.

Informacion que debe contener:

- Como analiza un problema.
- Como separa frontend, backend, datos y automatizacion.
- Como cuida mantenibilidad.
- Como usa Git.
- Como documenta o estructura proyectos.

Tiempo aproximado:
15 a 25 segundos.

Emocion:
"Puede integrarse a un equipo".

Accion que debe provocar:
Reforzar la decision de contactar o revisar experiencia.

Justificacion:
Linear y GitHub transmiten confianza mediante procesos claros. Para un desarrollador junior, mostrar criterio es una forma poderosa de diferenciarse.

### 7. Experiencia Profesional Resumida

Objetivo:
Presentar experiencia sin inflarla ni esconderla.

Informacion que debe contener:

- Participacion en RapiMecanica y GoClean.
- Desarrollo de automatizaciones.
- Desarrollo de software.
- Tipos de tareas realizadas.
- Tecnologias usadas en contexto.

Tiempo aproximado:
15 a 25 segundos.

Emocion:
Honestidad y progreso.

Accion que debe provocar:
Entender que Pablo tiene experiencia practica y potencial de crecimiento.

Justificacion:
La experiencia no debe aparecer como una cronologia vacia. Debe mostrarse como progreso profesional aplicado a problemas reales.

### 8. Stack Tecnologico Por Contexto

Objetivo:
Mostrar dominio tecnico de forma organizada.

Informacion que debe contener:

- Lenguajes: Python, JavaScript, PHP.
- Backend: Node.js, Laravel, REST APIs.
- Frontend: React.
- Base de datos: MySQL.
- Herramientas: Git.
- Especialidad diferencial: automatizacion con Python.

Tiempo aproximado:
10 a 20 segundos.

Emocion:
Orden y confianza tecnica.

Accion que debe provocar:
Validar rapidamente compatibilidad con una vacante.

Justificacion:
Un listado plano de tecnologias se olvida rapido. Agrupar por contexto ayuda al reclutador a mapear el perfil contra necesidades reales.

### 9. GitHub Como Evidencia Tecnica

Objetivo:
Convertir GitHub en prueba, no solo en icono.

Informacion que debe contener:

- Enlace al perfil.
- Repositorios destacados.
- Proyectos con README claro.
- Tecnologias visibles.
- Actividad o criterio de organizacion, si aplica.

Tiempo aproximado:
8 a 15 segundos.

Emocion:
Transparencia.

Accion que debe provocar:
Abrir GitHub para revisar codigo.

Justificacion:
GitHub funciona como validacion externa. Debe aparecer despues de los proyectos para que el visitante sepa que buscar.

### 10. LinkedIn Y Confianza Profesional

Objetivo:
Facilitar contacto profesional y validacion de identidad.

Informacion que debe contener:

- Enlace claro a LinkedIn.
- Mensaje de disponibilidad para oportunidades.
- Relacion con CV y contacto.

Tiempo aproximado:
5 a 10 segundos.

Emocion:
Seguridad.

Accion que debe provocar:
Abrir LinkedIn o enviar mensaje.

Justificacion:
LinkedIn es el puente natural entre interes y entrevista. Debe estar visible en hero, en contacto final y posiblemente despues de proyectos.

### 11. Certificados Curados

Objetivo:
Respaldar aprendizaje sin saturar la pagina.

Informacion que debe contener:

- Solo certificados relevantes para el rol objetivo.
- Nombre del certificado.
- Institucion.
- Tecnologia o area.
- Fecha si aporta confianza.
- Enlace o descarga si existe.

Tiempo aproximado:
8 a 15 segundos.

Emocion:
Disciplina y crecimiento.

Accion que debe provocar:
Validar formacion sin distraerse del trabajo real.

Justificacion:
Los certificados apoyan, pero no deben competir con proyectos. Deben aparecer despues de evidencia real.

### 12. CV Y Contacto Final

Objetivo:
Cerrar el recorrido con una accion simple.

Informacion que debe contener:

- Mensaje final orientado a entrevistas.
- CTA principal: contactar.
- CTA secundario: descargar CV.
- Enlaces a LinkedIn, GitHub y email.
- Disponibilidad o tipo de oportunidades buscadas.

Tiempo aproximado:
10 a 20 segundos.

Emocion:
Decision y facilidad.

Accion que debe provocar:
Enviar mensaje, abrir LinkedIn o descargar CV.

Justificacion:
La pagina debe terminar eliminando friccion. Si el visitante llego hasta aqui, no debe tener que buscar como contactar.

## CTAs Recomendados

### CTA Principal

Texto:
"Contactarme"

Donde aparece:

- Hero.
- Despues del proyecto principal.
- Cierre final.

Cuando cambia:

- En hero: "Contactarme".
- Despues de proyectos: "Hablemos sobre una oportunidad".
- En cierre: "Enviar mensaje".

Justificacion:
El texto debe volverse mas especifico a medida que el visitante avanza y ya tiene mas contexto.

### CTA Secundario

Texto:
"Ver proyectos"

Donde aparece:

- Hero.
- Prueba rapida de valor.

Cuando cambia:

- Antes de la evidencia: "Ver proyectos".
- En stack: "Ver trabajo aplicado".

Justificacion:
No todos los visitantes estan listos para contactar de inmediato. El CTA secundario guia hacia evidencia.

### CTA De GitHub

Texto:
"Ver codigo en GitHub"

Donde aparece:

- En proyectos con repositorio.
- En seccion GitHub.

Justificacion:
Debe estar cerca de evidencia tecnica, no perdido como icono global.

### CTA De LinkedIn

Texto:
"Conectar en LinkedIn"

Donde aparece:

- Hero como enlace secundario discreto.
- Contacto final como opcion destacada.

Justificacion:
LinkedIn reduce friccion para reclutadores y equipos que prefieren contacto profesional.

### CTA De CV

Texto:
"Descargar CV"

Donde aparece:

- No debe ser el CTA principal al inicio.
- Puede aparecer como accion secundaria en hero.
- Debe aparecer con mas fuerza al final, despues de que el visitante vio evidencia.

Cuando mostrarlo:

- En desktop, puede estar en la navegacion como accion discreta.
- En mobile, debe aparecer en el cierre y en menu si existe.
- Despues de proyectos, puede aparecer como "Descargar CV completo".

Justificacion:
El CV es util para reclutadores, pero si aparece demasiado dominante al principio puede sacar al usuario del recorrido antes de ver la evidencia diferencial.

## Psicologia Del Diseno

### Como Generar Confianza

- Usar afirmaciones concretas, no frases genericas.
- Mostrar proyectos reales antes que adornos visuales.
- Explicar problemas, rol y decisiones.
- Usar enlaces externos verificables.
- Mantener consistencia entre copy, stack y proyectos.

### Como Transmitir Profesionalismo

- Jerarquia clara.
- Pocos mensajes por seccion.
- Lenguaje directo.
- Espaciado generoso pero eficiente.
- Microcopy orientado a resultados.

### Como Evitar Saturacion Visual

- No mostrar todas las tecnologias en el primer bloque.
- No mostrar todos los certificados abiertos.
- No usar demasiados CTAs al mismo tiempo.
- Separar evidencia principal de evidencia secundaria.
- Mantener una idea dominante por seccion.

### Como Dirigir La Mirada

- Iniciar cada seccion con una frase clara.
- Usar jerarquia progresiva: promesa, evidencia, detalle, accion.
- Colocar CTAs despues de momentos de confianza.
- Destacar un solo proyecto como principal.

### Como Aumentar El Tiempo De Permanencia

- Abrir loops de curiosidad: "proyectos reales", "automatizaciones", "decisiones tecnicas".
- Dar suficientes detalles para invitar a profundizar.
- Permitir lectura por capas: resumen rapido y detalle opcional.
- Conectar cada seccion con la siguiente.

### Como Hacer Que El Usuario Quiera Ver Proyectos

- Presentar primero los problemas que Pablo puede resolver.
- Nombrar proyectos reales antes de mostrarlos.
- Hacer que el Featured Project parezca una historia, no una tarjeta.
- Mostrar tecnologias como herramientas aplicadas, no como logos aislados.

## Criterio De Exito

La experiencia estara funcionando si un visitante puede responder estas preguntas en menos de un minuto:

- Quien es Pablo Rodriguez Gil.
- Que tipo de desarrollador es.
- Que tecnologias maneja.
- Que proyectos reales ha desarrollado.
- Que evidencia externa puede revisar.
- Como puede contactarlo.
